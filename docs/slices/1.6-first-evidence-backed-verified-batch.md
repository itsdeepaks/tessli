## Goal

Run the Slice 1.5 human-operator workflow against the first small, independently reviewable set of Profiled sources and promote only records that satisfy every schema and semantic gate.

This slice creates the evidence packet, safe record-storage boundary, and explicit promotion machinery. It does not treat a drafted record, repository profile, available website, passing schema, or AI-assisted evidence review as proof that a source is currently Verified.

## Bounded candidate set

The first batch is limited to exactly three candidates:

| Candidate      | Why it belongs in the first batch                                                                                                           | Required boundary                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `google-fonts` | Exercises official product/documentation claims and a documented HTTP API that requires a user-owned key.                                   | The key may be used manually by the operator but must never enter a record, committed command, log, fixture, screenshot, or response artifact. |
| `radix-ui`     | Exercises an open-source component source with strong official accessibility and package documentation but no recorded agent interface.     | Package and documentation claims, current licence, attribution, redistribution, and limitations must be reviewed directly.                     |
| `react-aria`   | Exercises an open-source framework source with accessibility, interaction, and internationalization claims but no recorded agent interface. | Current framework scope, documentation claims, licence, attribution, redistribution, and limitations must be reviewed directly.                |

No fourth candidate may be added until these three records are completed, rejected, or explicitly returned to `needs-review`.

## Operator sequence

Run commands from `web/`. Incomplete drafts belong in the repository-ignored `verification-work/` directory.

```bash
npm run verification:draft -- google-fonts --reviewer deepak-sing --name "Deepak Sing" --date 2026-08-06 --output ../verification-work/google-fonts.json
npm run verification:draft -- radix-ui --reviewer deepak-sing --name "Deepak Sing" --date 2026-08-06 --output ../verification-work/radix-ui.json
npm run verification:draft -- react-aria --reviewer deepak-sing --name "Deepak Sing" --date 2026-08-06 --output ../verification-work/react-aria.json
```

Use `docs/verification/1.6-evidence-packet.md` to reduce research time. The packet is AI-prepared supporting research, not a completed human review.

For each candidate, the human operator must:

1. verify the canonical destination and identity in a normal browser;
2. review every copied claim against current official evidence;
3. manually test every recorded agent interface when one exists;
4. review persistence, redistribution, attribution, and current terms or licence documentation;
5. review the profile limitations;
6. record complete dates, freshness, a recheck deadline, and decision notes;
7. run `npm run verification:check -- <record-path>`;
8. stop promotion when the result is invalid, stale, `needs-review`, or `rejected`.

Completed records that are safe for repository review belong under `verification-records/1.6/`.

## Explicit promotion contract

Promotion requires all three independent gates:

1. the intelligence profile is deliberately changed to `status: verified` with truthful human-review provenance;
2. a completed repository record passes JSON Schema and semantic validation with `eligibleForPromotion: true`;
3. the canonical resource ID is deliberately added to `verification-records/promotions.json`, and the generated promotion registry passes drift checks.

A record alone cannot promote coverage. Profile status alone cannot promote coverage. Human-review metadata alone cannot promote coverage.

The profile provenance must identify `status: completed`, the exact reviewer ID, completion date, and canonical repository record path. Those values must match the generated promotion entry, and its `recheckBy` date must remain current against Tessli's deterministic source-profile review date.

Commands:

```bash
npm run verification:promotions:generate
npm run verification:promotions:check
```

## Acceptance criteria

- keep the batch fixed at three named candidates;
- prepare current official-source evidence without representing AI research as human completion;
- create no automated provider, browser, HTTP, API, CLI, MCP, pricing, terms, licence, credential, or availability claim;
- require a genuine `human-operator` reviewer for every completed record;
- validate every completed record against `tessli.resource-verification.v1` and current canonical source/profile truth;
- reject stale fingerprints, altered claim/interface sets, impossible or misordered dates, incomplete checks, contradictory evidence, unsafe Verified decisions, and secret-bearing fields;
- require manual browser availability checks and the interface-specific manual test method; documentation review alone cannot pass a recorded API, MCP, CLI, SDK, or plugin interface;
- keep incomplete drafts in the ignored `verification-work/` directory;
- retain only completed safe records under `verification-records/1.6/`;
- require an explicit promotion list and deterministic generated promotion registry;
- ensure missing, stale, invalid, duplicated, `needs-review`, rejected, or non-eligible records cannot enter the promotion registry;
- ensure source coverage consumes the generated promotion registry and cannot be upgraded by profile or review metadata alone;
- promote only records with `valid: true` and `eligibleForPromotion: true` after complete diff review;
- keep Listed, Profiled, and Verified coverage truthful and preserve a total of 295 sources;
- align website, public representations, MCP, catalogue, README, Product Plan v2, and build ledger with the exact promoted set;
- run focused verification tests plus formatting, TypeScript, lint, full tests, promotion drift, catalogue drift, build, browser, and release gates;
- retain complete operator evidence and rollback instructions without storing credentials or private provider content.

## Exclusions

- no invented human review, current availability, interface result, terms conclusion, licence conclusion, or evidence date;
- no source outside the three-candidate batch;
- no automatic promotion from a valid draft, completed record, human-review field, or schema-only result;
- no paid/private provider content, screenshots, downloaded assets, customer data, workspace content, cookies, tokens, passwords, API keys, or session values;
- no redesign, auth, cloud workspace, submission, moderation, analytics, email, deployment, or proof-track change;
- no change to the separate blocked Slice 5.3 human-review dependency.
